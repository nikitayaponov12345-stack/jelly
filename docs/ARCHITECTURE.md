# ARCHITECTURE — «Желейный легион» (v1.0, 09.10.2026)

Как устроен код и какие правила в нём не нарушаются. Правила игры и числа — в `docs/GDD.md` (выгрузка Claude Doc «Желейный легион: GDD»), в таблицах `data/` и в файлах уровней `data/levels/`. Образец физики и застывания — прототип `docs/research/prototype.html`.

## 1. Инварианты

1. **Ядро без отрисовки.** `src/core/` — чистый TypeScript: без PixiJS, DOM, `window`, `localStorage`, `performance.now()` и `Math.random()`. На ядре идут тесты Vitest, бот-решатель и подсказка-призрак.
2. **Время — только игровое.** Логика шагает фиксированным шагом `FixedStep` (60 шагов в секунду игрового времени); внутри ядра шаг — `dt = 1/60 с`, единицы — клетки и секунды. За долгий кадр выполняется столько шагов, сколько положено (не больше 8 за кадр).
3. **Попытка уровня детерминирована.** Одинаковый уровень и одинаковые команды на одних и тех же шагах дают одинаковую игру до бита: в правилах нет случайности вообще. Случайность (частицы, позже генератор «башни дня») — только `Rng` с сидом и только вне правил попытки.
4. **Числа баланса — только из `data/constants.csv`, уровни — только из `data/levels/*.txt`.** В коде нет чисел баланса; допустимы константы раскладки экрана (`src/game/layout.ts`) и технические (шаг 60 в секунду, предел шагов за кадр).
5. **Формулы прототипа — дословно.** Порядок действий в шаге желейки (буфер прыжка → гравитация → движение по вертикали и опора → движение по горизонтали и стена → койот → продвижение и лопание → угрозы) и формулы столкновений переносятся из прототипа без «улучшений»; тесты сверяют числа с прототипом. Отличия — только названные в GDD и в задаче.
6. **Строки интерфейса — через `translations/strings.csv`** (ru, en). Текст в код окон не вписывается.
7. **Площадка — только через интерфейс `Platform`** (`src/platform/platform.ts`). SDK площадок вызываются только в адаптерах; в коде игры нет сетевых запросов.
8. **Ввод — командами.** Слой ввода превращает нажатия в команды ядра `press()`, `release()`, `restart()`. Ядро не знает про мышь, палец и клавиши; бот подаёт те же команды между шагами.
9. **Отрисовка только читает.** `src/game/` и `src/ui/` читают состояние ядра и его события и рисуют; правил не решают и состояние ядра не меняют иначе как командами.
10. **Файл — не длиннее 400 строк;** на каждый модуль ядра — тесты; новая механика приходит с тестом, который без неё падает.

## 3. Координаты и экран

- **Уровень — сетка клеток** `grid_cols × grid_rows` (24 × 13). Точка `(x, y)` — в клетках, `y` вниз; клетка `(c, r)` = `[c, c+1) × [r, r+1)`. За левым и правым краем поля — стены, выше верхнего края — воздух, ниже нижнего — пропасть.
- **Экран — точки дизайна:** 1280 × 720 в горизонтали, 720 × 1280 в портрете; раскладку выбирает соотношение сторон окна (`layoutFor`), экран вписывается целиком (`fitDesign`).
- **Поле** (`FIELD` в `layout.ts`): в горизонтали — весь уровень, клетка 50 точек; в портрете — окно 720 × 728 с клеткой 56 точек и камерой за желейкой (желейка на доле `camera_lead` ширины окна, догоняние `camera_smooth`), под ним — карта всего уровня (`MINIMAP`, клетка 30) — решение Никиты 09.10.
- Камера — часть отрисовки, не ядра: ядро не знает, что видно на экране.

## 4. Данные

- CSV — UTF-8 без BOM, разделитель запятая, текст с запятой — в кавычках, пустая ячейка — «нет значения».
- Уровни — текстовые файлы `data/levels/<набор>.txt`; формат — `data/README.md`. Набор = мир (`data/worlds.csv`, колонка `file`).
- `src/core/data/tables.ts` превращает текст в таблицы и проверяет заголовки и числа (ошибка — исключение с именем файла и строкой); `src/core/levels.ts` разбирает уровни по тем же правилам, что `tools/data-check.mjs`.
- `src/data.ts` импортирует файлы через `?raw` (Vite встраивает их в сборку) и отдаёт `DATA`. Новый файл уровней — импорт в `src/data.ts` и строка в `data/worlds.csv`.
- `tools/data-check.mjs` (`npm run data`) проверяет всё вместе. Входит в `npm run check` первым.

## 5. Цикл кадра

```
событие ввода (pointerdown / pointerup по холсту, keydown / keyup по окну, кнопка «Заново»)
  └─ OneButton (input.ts) → run.press() / run.release() / run.restart()   сразу, между шагами: следующий шаг их видит
       в окне итога нажатие после паузы done_input_delay_s — «Дальше», в итоге набора — «Сначала» (PackFlow, flow.ts)
ticker (кадр PixiJS)
  └─ FixedStep.advance(кадр, шаг):     ядро шагает в игровом времени (не больше 8 шагов за кадр)
       └─ run.step(dtMs)               желейка, угрозы, застывание, плиты и двери, таймеры
  └─ flow.frame(кадр, run)             финиш попытки → итог уровня и окно итога; пауза окон
  └─ scene.sync(кадр)                  события шага (run.drainEvents) → сквош, частицы, тряска; камера; отрисовка
  └─ hud.update, windows.show…         строка счёта, надписи над полем, окна (M0-03)
```

Анимация, частицы, камера, надписи и пауза окон идут во времени кадров (`ticker.deltaMS`; PixiJS ограничивает его 100 мс): это вид и интерфейс, на правила попытки они не влияют. При частоте ниже 10 кадров в секунду игра замедляется, а не перескакивает.

Команды не копятся в очередь: ядро запоминает их как состояние (нажатие ждёт в буфере прыжка `jump_buffer_s`, удержание включено), а шаг решает, что из этого следует. Пауза (окно, реклама, свёрнутая вкладка) — ядро не шагает; часы `FixedStep` не копят время паузы.

## 6. Попытка уровня (`Run`)

- Состояния: `ready` — первая желейка стоит на старте, время и лазеры стоят (решение Никиты 09.10); `play` — идёт попытка; `done` — желейка дошла до флага. Первое `press()` в `ready` только запускает бег (без прыжка). `restart()` из любого состояния возвращает `ready`: тел нет, легион 0, время 0.
- В `play`: живая желейка или пауза возрождения (`respawn_s`) после гибели; тела копятся; легион = число гибелей.
- Шаг отдаёт события для отрисовки и звука: прыжок, приземление, гибель (причина, точка), застывание (клетка), возрождение, финиш. Отрисовка читает их после шага; на правила они не влияют.

## 7. Слой площадки

`Platform`: `init`, `loadingFinished`, `gameplayStart`, `gameplayStop`, `showInterstitial`, `showRewarded`, `save`, `load`, `language`. С M4 — адаптеры: `bridge` (Playgama Bridge: Яндекс, CrazyGames, Playgama) и `poki` (отдельная сборка без покупок). Реклама решается игрой заранее (`data/ads.csv`), адаптер только показывает.

## 8. Сохранение (с M1)

Одна запись JSON `{ version, levels, fallen, skins, settings, ads }`: `levels` — по id уровня лучшие звёзды, легион и время; `fallen` — счётчик павших за всё время; `ads` — время последней межстраничной. Недоигранный уровень не сохраняется (решение 09.10). Запись — после итога уровня и при сворачивании. Новая версия записи переводит старую, а не сбрасывает.

## 9. Отладка и боты

`window.__game` (`src/debug.ts`) — чтение состояния и команды для тестов и ботов; этап 0 — заглушка; M0-01 задаёт состояние попытки и команды (`levels()`, `setLevel(id)`, `state()`, `command.press/release/restart`, `advance(ms)`), M0-02 — `toScreen` (точка уровня → точка окна), чтение камеры `camera()` и `pauseCore(on)` — остановка шагов ядра в тикере для снимков и проверок вида (кадры идут, `advance` работает); M0-03 — `screen()` (уровень, окно итога, итог набора) и `showPack()`; дальше расширяется задачами. В выпуске (M4) отключается флагом сборки; `?debug=1` показывает отладочную строку.

## 10. Бюджеты

- Сборка до старта — не больше 3 МБ сжатых данных (`tools/size-report.mjs` падает при превышении).
- Загрузка до игры — до 4 с; 60 кадров в секунду на телефоне Никиты со ста телами на поле.
- `npm run test` — до 30 с; долгие прогоны бота — отдельной командой: `npm run solve` (M0-04) — около 20 с на шесть уровней прототипа.

## 11. Порядок выполнения задачи

Задача из `docs/tasks/` → код и тесты → `npm run check` зелёный → строка статуса «сделано ДД.ММ» в `docs/tasks/README.md` → отчёт (что сделано, итоги `npm run check`, что не получилось и почему). Спорное — в отчёт, а не в код. Коммит и push делает Никита.
